# 달력 스크린샷 인식 전수 점검: 화면 크기·테마 독립 판독

이전 작업: [Android 메모리](android-image-investigation.md) → [화면 비율 대응](adaptive-calendar-layout.md) → [Galaxy 가림 경계](galaxy-occluded-boundary.md)

## 확인한 자료

- 기준: `origin/main` `71481dd`.
- 처음에는 `tests/fixtures/private/`가 비어 있었다(실제 17 Pro Max·다크·Galaxy 원본 없음).
- 이후 사용자가 **실제 iPhone 다크 화면 3장**(2026.09·10·12, 1188×2576 PNG)을 제공했다. 원본은 `private/`(gitignore)에만 두고,
  `scripts/deidentify-fixtures.mjs`(가림 색 검정)로 만든 `deid-dark-*.png`만 공개 fixture로 쓴다.
- 실제 iPhone 17 Pro Max 원본은 여전히 없다. 17 Pro Max 원인을 확정하거나 "지원 완료"를 주장하지 않는다.
- 재현 자료는 공개 비식별 fixture에서 만든다(`tests/deviceLayout.ts`).
  - 재배치(transformed): 글자·원·제목은 pt 크기를 유지하고 7열·주 행만 화면에 맞게 늘어나는, 실제 앱과 같은 방식의 배치.
    750×1334(2x)부터 1320×2868(440pt), Android 720/1080/1440 폭까지 8종.
  - 합성 다크(synthetic): 밝기 극성만 바꾼 두 가지(검은 바탕 반전, 짙은 회색 바탕 + A/B/휴 색 유지). 실제 팔레트가 아니다.

## 재현 결과 (origin/main 판독기)

| 입력 | 결과 | 실패 단계 |
| --- | --- | --- |
| 단순 축소·확대 600~1440px 18종 × 10개월 | 전부 통과 | — |
| 재배치 8종(1320px 계열 포함) × 10개월, 라이트 | 전부 통과 | — |

| 하단 **중앙**을 가리는 작은 원/둥근 사각형 | 실패(`cropped`) | 마지막 경계선이 두 조각(각 43%)으로 나뉘어, 한 조각 60% 이상만 인정하던 규칙에 걸림 |

1320px 계열은 라이트에서 재현되지 않았다. 사용자가 본 실패가 화면 크기 자체 때문이라는 증거는 찾지 못했다.
재현된 원인 중 17 Pro Max 사용자에게 해당할 수 있는 것은 **기기 다크 모드(자동 포함)** 와 **하단 중앙을 가리는 떠 있는 UI** 두 가지다.
실제 원본 없이 어느 쪽인지 확정할 수 없다.

## 실제 다크 화면으로 추가로 확인한 것

합성 다크만으로 만든 1차 수정(`feee781`)에 실제 다크 화면을 넣자 공개 비식별 테스트 9개 중 8개가 실패했다.

| 실제 화면 특징 (측정값) | 1차 수정의 결과 | 원인 · 수정 |
| --- | --- | --- |
| 검은 바탕, C 원 rgb(66,66,66) (대비 0.26) | 9·10월 `low-confidence`, **12월은 C 6일을 확신도 0.3의 '휴'로 둔 채 성공** | C 기준 대비 0.45가 라이트 화면에만 맞음 → 0.2 (앞뒤 달 흐린 원: 흰 바탕 0.15, 검은 바탕 0.05~0.19, 이번 달 칸에는 없음) |
| 오늘 칸 전체가 남색 (10,45,84) | 9/30 C를 B로 읽을 위험 | 칸마다 바탕색을 추정해 그 색은 표시로 세지 않음 |
| 오늘 칸이 첫 주(10월 화면의 9/30) | 격자 없음 (`not-calendar`) | 끊긴 윗경계를 합친 선이 목록 끝에 붙어 위→아래 짝을 못 찾음 → y 순 정렬 |

수정 후 실제 다크 3장(원본·비식별본, 600~1440px, JPEG·WebP)과 라이트+다크 혼합 등록이 날짜별 정답과 모두 일치한다.
재배치 생성기도 실제 화면처럼 강조 칸 전체를 칠하도록 고쳤다(`tests/deviceLayout.ts`).

## 변경

- `theme.ts`: 달력 영역의 배경(가장 흔한 밝기)을 사진마다 추정하고, 모든 판정을 "배경에서 글자 쪽으로 얼마나 멀어졌는지(대비 0~1)"로 한다.
  라이트(검은 글자)와 다크(흰 글자)가 같은 값이 된다. 두 장의 테마가 달라도 각각 추정한다.
- 격자(`grid.ts`): 절대 밝기 대신 "양쪽 모두보다 어둡거나 양쪽 모두보다 밝은 얇은 회색 선". 같은 높이에서 가림 때문에 끊긴 조각은
  실제로 보이는 길이만 합쳐 60% 규칙을 적용한다(가린 폭이 40% 이하일 때만 합침). 보이지 않는 행은 여전히 만들지 않는다.
- 원/휴(`pixels.ts`, `markers.ts`, `analyze.ts`): 색 원은 채도·색상각, C 원은 배경 대비 0.2 이상 무채색, 휴는 빨강 색상각.
  칸 자체의 바탕색(오늘 강조 등)과 같은 픽셀은 표시로 세지 않는다.
  배경과 조금만 다른 원(대비 0.1~0.2)만 있고 휴 글자도 없으면 휴로 단정하지 않고 확신도 0.3(확인 필요)으로 둔다.
- 날짜 잉크(월 배치 검증): 사진 스스로의 이번 달 글자 대비의 55%를 기준으로 한다(상한은 기존 흰 바탕 기준).
- 제목(`title.ts`): 제목 줄 배경 대비로 잉크를 재서 같은 숫자 기준표 한 벌로 두 테마를 읽는다. 흰 바탕에서는 기존 값과 같다.
- `dark-mode` 오류를 없앴다. 어두운 단색 이미지는 격자가 없으므로 `not-calendar`로 거부된다.
- 오류 안내를 원인별로 나눴다: 사진 열기 실패 / 잘림(제목부터 마지막 주까지) / 다른 달(사진 속 제목) / 일부 표시 흐림(직접 입력에서 확인·수정) / 달력 아님.
- `loadImage.ts`: 분석 크기 계산을 `analysisSize()`로 분리(동작 동일: 폭 1440px·4백만 픽셀 이하, 1320×2868은 원본 크기 유지). 테스트도 같은 크기로 분석한다.
- 개발용 `diagnostics.ts`의 `diagnose()`: 이미지·배경·격자·제목·원 집계·월 적합도·실패 단계. 앱 화면에는 쓰지 않는다.
- 라이트 사진의 사진 지문(중복 등록 확인)은 기존과 비트 단위로 같다. 다크 사진은 밝기를 뒤집어 같은 달력이면 같은 지문이 된다.

## 검증

- 새 회귀 67개 중 26개가 origin/main에서 실패, 수정 후 전부 통과. 기존 단위 테스트는 어두운 단색 이미지 기대값만
  `dark-mode` → `not-calendar`(여전히 거부)로 바꿨다.
- 로컬 스트레스(`npm run test:analyzer:stress`): 재배치 8종 × 테마 3종 × 10개월 + 폭 18종 × (라이트 10개월 + 실제 다크 3개월) = 474장 전부 날짜별 정답 일치.
- 실제 다크(`tests/dark-real.test.ts`, `e2e/theme-device.spec.ts`): 비식별본은 CI에서, 원본은 로컬에서 날짜별 정답·7회 확인.
- 안전성: 다른 달(라이트·다크), 큰 잘림, 좌우 열 잘림, 마지막 행 대부분 가림, 강한 흐림, 가로 회전, 원 없는 7열 표는 자동 통과하지 않는다.
- 분석 시간(Node, 두 장): 1179px 약 260ms, 1320px 약 280ms (기존 약 160ms). 캔버스·버퍼 수는 그대로다.
